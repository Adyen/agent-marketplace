# ADR 0011: Cooldown clocks and history-rewrite refusal

**Status:** Accepted (2026-11-02)

## Decision

A cooldown delays candidate selection until a resource revision or Git commit has been observable for a configured period, so that a compromised registry's malicious change can be noticed and revoked before consumers advance to it. The cooldown gates only advancing: an existing pin or lock is never re-evaluated, `sync` never consults ages when it reuses a pin or lock, and only candidate selection (`install`, `update`, `lock --upgrade`, and a writing `sync` performing an initial acquisition) applies it.

Each source kind uses the strongest clock available to it:

- **Marketplace sources** measure from **first publication**: the time the Marketplace first recorded a registry occurrence containing the resource revision. It is server-assigned, keyed by content digest, and unchanged by reassessment, archive-digest repair, or registry moves. A revert to previously published content is therefore immediately eligible, and a newly approved registry or a from-scratch metadata database holds everything for one period.
- **Git sources** measure from the **effective commit date**: the later of a commit's committer date and the effective commit date of its first parent (and, for an annotated tag, the tagger date). Within the measured first-parent history a commit is never considered older than its ancestors, so a backdated commit pushed on top of a recent tip is simply young. Selection is anchored at the locked commit: the candidate is the newest first-parent descendant of the locked commit that is old enough, which may be older than the tip. The guarantee is bounded by that history: on a branch whose newest real commit is itself older than the period, a push backdated to that commit's date is accepted immediately. The Git clock therefore shortens the window on active branches; it does not provide an observation period on dormant ones, and the documentation says so.
- A consumed branch whose locked commit is no longer an ancestor of its tip is a **history rewrite** and is **refused**, not aged out, whenever a cooldown period is configured. Acceptance is an explicit, optionally targeted flag on `update` and `lock --upgrade` (and a confirm modal in the TUI); the resulting lock is the only record of acceptance, and an accepted rewrite whose history is still entirely young is held, not taken. With the period at its default of zero, `update` keeps today's behavior of following the tip, so enabling the cooldown is what opts a consumer into the refusal. `--bump` across tags requires no ancestry and measures back to the merge-base.
- **Initial acquisition** is deliberately asymmetric. A Git source with no lock has no anchor, so if its whole history is young the tip is taken with a warning: the person writing `git: <url>` made the trust decision. A Marketplace coordinate with no pin whose revisions are all young requires an explicit acknowledgement, because catalog names are confusable and typosquats live there. Operators and organizations can make either strict.
- The cooldown is a **floor that consumer layers may only raise**: organization, then user, repository, personal-local; a lower value is clamped to the floor with a warning. The Marketplace operator sets a separate server floor that clients never lower, and, because the operator owns that floor, may vary it per registry in either direction; in the first change that override exists for file-mode operator configuration, and database-managed registries gain it in the follow-up that moves cooldown into the managed snapshot. The built-in default is zero on both sides; documentation recommends a 24-hour organization floor.
- A hold is **never a distribution control**. The Marketplace withholds a held revision only from latest-revision resolution; exact-digest acquisition keeps working so that pins recorded before a floor was raised still resolve on a fresh machine. An operator's `held: strict` tells conforming clients not to offer acknowledgement; hard denial remains the job of revocation.

Normative behavior belongs to the OpenSpec specifications that implement this decision; this ADR records why the clocks and refusals are shaped as they are.

## Alternatives rejected

- **Commit or assessment time as the Marketplace clock.** Commit dates are written by whoever controls the repository; assessment time resets on every analyzer or policy re-run.
- **Local first-observed time for Git**, alone or combined with committer dates. It resists backdating on dormant branches, but every update becomes a two-step wait and it gives no answer for initial acquisition, which is exactly when a new consumer is most exposed. The causality rule covers the active-branch case without that cost. An opt-in observed clock remains a possible follow-up for consumers who accept the two-step update.
- **No Git cooldown.** Rejected because the effective-commit-date rule with a locked anchor does hold against a compromiser who pushes onto an active branch; history rewriting defeats it and is refused separately, and dormancy is documented as the residual.
- **Aging out a history rewrite** instead of refusing it. Waiting would launder the one event that defeats the Git clock.
- **Refusing history rewrites regardless of the period.** It is the stronger control, but it changes the outcome of `update` for consumers who never opted into a cooldown and would need a major release; it stays available as a follow-up.
- **Denying distribution of held revisions server-side (`held: block`).** It would refuse artifacts for revisions already pinned inside a later-raised floor, breaking existing installations on fresh machines, and it could not cover index-only acquisition, which never downloads an artifact. The operator's strictness is therefore a signal to conforming clients, not a gate.
- **A runtime flag to bypass a held update.** A hold on an existing pin is a policy outcome; the reviewable bypass is an exact pin in committed configuration (full commit ID or exact `revision:`), which an organization layer can see and constrain. The one runtime flag, `install --acknowledge-cooldown`, exists only for a Marketplace initial acquisition with no eligible revision, pins a floating installation, and can be disabled by `initial_acquisition: strict` or the operator's `held: strict`.
- **Database-managed cooldown in the first change.** Cooldown is a distribution policy like `rejected_resources` and will follow it into the managed snapshot; the first change keeps it in operator YAML with file-mode per-registry overrides.

## Consequences

- After an accepted history rewrite the Git cooldown offers no protection against an attacker who also wrote the dates; the refusal and its evidence are the only control, and the refusal text must say so.
- First acquisition of a Git source trusts the publisher's dates by design. A new consumer adding an established repository still gets the newest old-enough commit, not the tip.
- Adding a new resource to an already-locked Git source is an update of that source and is held like any other; commit-level locking cannot distinguish it from a malicious addition.
- Raising a floor never disturbs existing installs; it only delays future advances. First publication is used only for the eligibility cutoff; ordering is by registry occurrence. A cooldown-aware client never selects a candidate whose most recent registry occurrence is older than the current pin's; when the head is held, the fallback is the most recent eligible registry occurrence, so a rolled-back revision is not restored, and following the head to previously published content after a revert is an ordinary update, not a cooldown decision. A client that predates the cooldown has no such rule: with its pin inside a newly raised server floor, `update` follows the fallback and may step back to the most recent eligible occurrence, so operators upgrade clients before enabling a non-zero floor or accept that step-back.
- A collection revision is eligible only when every member revision it selects, transitively, is eligible under its own registry's period and the consumer's floor; otherwise the collection is held, because expanding it would acquire the held member by exact digest.
- Clients compute the effective Marketplace cooldown as the maximum of the server floor and their own; against a server that does not expose first publication, the client warns and proceeds unless configured to refuse.
- Older clients reject unknown configuration fields, so a shared configuration gains `cooldown` only after every client that reads it has been upgraded; the rollout order is part of the documentation.
